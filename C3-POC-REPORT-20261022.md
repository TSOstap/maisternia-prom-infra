## Стабільна HTTPS-адреса

`https://mm-feed-poc.<піддомен>.workers.dev/feeds/main.xml?key=…` — не змінювалась за всі деплої й відкати (адреса не залежить від версії). Обмеження: Cloudflare пише, що `workers.dev` «intended for personal or hobby projects» і радить для продакшну власний домен/route. Власний домен потребує домену в Cloudflare — окреме рішення власника. Як Prom поводиться з цією адресою, не перевірялось (за умовою).

## Обмеження, які треба врахувати для реальних фідів

1. **Static assets не віддають Content-Length** (і локально, і в Cloudflare) — розмір частини до відповіді не перевірити; захист — перевірка перед деплоєм, `FixedLengthStream` і readback.
2. **Subrequests:** ≤48 частин на фід (~1,1 ГБ) — з великим запасом до прогнозу 30 тис. товарів (≈290 МБ). Рекомендація Prom «до 180 МБ на файл» досягається раніше.
3. **Завантаження нової версії:** 49 МБ — ~16 с, 289 МБ — ~43 с з локальної мережі (з GitHub Actions ще не вимірювали).
4. **Загальний обсяг assets на акаунт/версію і накопичення старих версій** — в офіційній документації ліміту не знайдено; при щоденних деплоях стежити.
5. Денного ліміту деплоїв не знайдено; для 6 деплоїв/добу проблем не очікується (за тест ~11 за ~10 хв).
6. `workers.dev` — див. вище.

## Що лишилось у Cloudflare

Worker `mm-feed-poc` (Free), активна версія **B** (синтетика, з захистом HTTPS), доступ лише за ключем. Нічого іншого не створено. Видалити можна однією командою — за рішенням власника.

## Наступні кроки C3 (кожен — окреме погодження)

1. C3-1: публікатор у конвеєрі (`src/`): розбиття, маніфест, upload → deploy → readback → авто-відкат; запуск із GitHub Actions (секрет із токеном Cloudflare, поки без розкладу) — виміряти час завантаження з runner.
2. C3-2: shadow-публікація **реального** фіду за секретною адресою, не підключеною до Prom; порівняння байт-у-байт із чинним YML.
3. Рішення щодо домену: `workers.dev` чи власний.
4. Тестове посилання для Prom (окремий тестовий імпорт або перевірка без імпорту) — лише після погодження, C4/C5.
