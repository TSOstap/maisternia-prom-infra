# S1: запис нової системи в КОПІЮ Google-таблиці — план (22.10.2026)

Рішення власника (22.10.2026): варіант A — Google Sheets лишається основною базою товарів. «Нові товари» стає постійною чергою СИРИХ позицій постачальника; NEW92 переноситься в «Основний каталог» (разом 5121). Затвердження — колонка «Рішення». SEO заповнює власник вручну. Усе — лише на КОПІЇ таблиці.

Жива таблиця, Apps Script/mtUpdate, чинні YML і Prom не змінюються. Розклад не вмикається.

## 1. Цільова модель (у копії)

| Аркуш | Вміст | Хто пише |
|---|---|---|
| Основний каталог | готові SEO-товари, що йдуть у Prom (5029 + 92 = 5121) | нова система: лише 8 операційних колонок (ціни, наявність, стан, «Оновлено») + додавання затверджених рядків |
| Нові товари | черга сирих позицій постачальника: ID, артикул, назви, опис, фото, характеристики, ціна, наявність — оригінальні дані постачальника; + колонки «Рішення», «Перевірка», «Виявлено» | нова система додає нові позиції й оновлює їхні ціни/наявність; власник заповнює SEO і ставить «ЗАТВЕРДЖЕНО» |
| Відкладені товари, Заморожені ID, Групи | як зараз | не змінюються системою |
| Журнал | кожна зміна: дата, аркуш, ID, поле, було, стало | нова система (як mtUpdate) |

## 2. Логіка одного запуску (кожні 4 год — у майбутньому; зараз лише вручну)

1. Прочитати таблицю (копію) і повний XML постачальника.
2. **Ціни й наявність**: ті самі формули, що в LIVE (паритет доведено в C2-C/C3-2). Пишуться ЛИШЕ 8 операційних колонок; SEO, фото, характеристики та інші поля не перезаписуються. Після запису — readback і перевірка печаток (`SHA256 незмінних полів`): якщо змінилось хоч одне незмінне поле — відкат запису.
3. **Зникнення в постачальника** — правила D1/D1b: «немає в наявності», картка й контент лишаються; масові зникнення (поріг аномалії) — нічого не записується.
4. **Нові позиції** → «Нові товари», без дублікатів: не додається, якщо ID вже є в «Основному каталозі», «Нових товарах», «Відкладених», «Заморожених ID» або в реєстрі перев'язок D1; позиція, схожа на наявну картку (можливий новий ID того самого товару), — не додається, а позначається в «Перевірці» для ручного рішення.
5. **Затвердження**: рядок у «Нових товарах» з «Рішення» = «ЗАТВЕРДЖЕНО» перевіряється (назви UA/RU, описи, 1–10 фото, група, категорія Prom, ціна, наявність). Якщо все гаразд — переноситься в «Основний каталог» **з тим самим Offer ID**, отримує печатку й «ДОЗВОЛЕНО», зникає з «Нових товарів», паспорт погодженого набору оновлюється з записом у журналі (хто/коли). Якщо ні — причина пишеться в «Перевірку», рядок лишається.
6. YML основного каталогу → тіньовий Worker (як C3-2).

## 3. NEW92 → Основний каталог (у копії)

- 92 рядки переносяться без змін: ті самі Offer ID, весь контент, печатки, ціни/наявність.
- Перевірки: 5121 унікальний ID; 0 перетинів із «Відкладеними»/«Замороженими»; печатки всіх 92 = до переносу; YML 5121 = YML main (5029) + YML NEW92 (92) за змістом кожного offer (порівняння з чинними посиланнями — лише читання).
- Розмір об'єднаного YML ≈ 49,96 МБ (оцінка: 49 061 950 + 915 267 мінус повторний заголовок) — фактично на межі ліміту Apps Script (50 МБ), і LIVE `MTY.count` = 5029. **Тому в живій таблиці об'єднання можливе лише ПІСЛЯ переходу Prom на новий фід** (окремий етап і погодження).

## 4. Безпека

- Службовий акаунт має «Редактор» лише на КОПІЮ; на живій таблиці лишається «Читач» → Google сам не дасть записати в живу таблицю. Додатково код відмовляється писати, якщо ID таблиці = ID живої.
- Запис — пакетний; перед записом знімок попередніх значень у пам'яті; невдала перевірка → повернення попередніх значень (як mtUpdate).
- У журнали GitHub — лише агрегати (захист від витоку, як у C2-C/C3-2). Реальні дані не потрапляють у репозиторій чи артефакти.
- Копія таблиці містить копію прив'язаного Apps Script: у копії **нічого не запускати з меню**; тригери за часом перевіримо, що їх немає.

## 6. DONE / STOP

**DONE:** у копії 5121 товар, усі ID/SEO/печатки збережено; ціни й наявність оновлюються без зміни SEO; нові позиції додаються без дублікатів; затверджений рядок переноситься з тим самим ID і зникає з черги; зникнення обробляються за D1/D1b; YML 5121 = main + NEW92 за змістом; тести PASS; журнали без витоків.

**STOP:** будь-яка спроба запису в живу таблицю; зміна незмінного поля під час синхронізації; невдалий readback; потреба в платних ресурсах; розбіжність YML 5121 з чинними фідами, яку не пояснено часом знімка.

## 7. Уточнені правила власника (22.10.2026) — реалізовано локально

| Правило | Як працює |
|---|---|
| Товар зник із коректного XML | лишається в основному каталозі: «-», «ВІДСУТНІЙ_У_YML»; ціна, SEO, ID — без змін; у YML — «немає в наявності» |
| Повернувся з тим самим ID | ціна й наявність оновлюються (якщо змінились артикул/назви — стан конфлікту, чекає власника) |
| Той самий товар з іншим ID або артикулом | у «Нові товари» з «МОЖЛИВИЙ ДУБЛЬ: <Offer ID> («аркуш»; зник із фіду) — оцінка; збіг: …; фото: …; різниця комплектації: …». Ознаки: артикул, назви UA/RU, бренд+модель, сторінка постачальника, фото (номери зображень), комплектація (назви й характеристики: к-сть/ємність АКБ, «без АКБ», зарядний, кейс, напруга, потужність) |
| Фото | спільні — сильна ознака (на реальних даних 5027/5029 карток мають усі фото спільні з «своєю» позицією); різні — показуються закінчення обох посилань; остаточного рішення лише за фото немає |
| Позначки схожості | «МОЖЛИВИЙ ДУБЛЬ» — схожість із товаром основного каталогу/відкладених; «СХОЖІ ПОЗИЦІЇ В ЧЕРЗІ» — лише з іншими новими позиціями. Збіг лише за сторінкою постачальника не враховується (на реальних даних — спільні slug різних моделей) |
| Можливі дублі не відкидаються | лише позначка; затвердження позиції, схожої на товар основного каталогу, — тільки «ЗАТВЕРДЖЕНО (НЕ ДУБЛЬ)» |
| «ПРИВ'ЯЗАТИ ДО <Offer ID>» | лише рішенням власника. Зберігаються Offer ID, SEO, фото, характеристики картки; новими стають ID постачальника, «Артикул постачальника», «Код товару Prom» (завжди = новий артикул; старий код — в історії), назви/URL постачальника. Історія — аркуш «Історія прив'язок» (старі/нові значення, підстава, стан). Відмова з поясненням, якщо: товару немає в основному каталозі; позиції немає у фіді; стара позиція досі у фіді; ID постачальника вже в іншого товару; новий артикул уже має інший товар (як артикул або «Код товару Prom»); у позиції немає артикулу; кілька позицій на один товар; будь-який сумнів (різна комплектація, бренд, різні назви постачальника, різні або частково різні фото, немає фото) без «(ПІДТВЕРДЖУЮ)» — з переліком відмінностей |
| Скасування прив'язки — у будь-який момент | «СКАСУВАТИ» в «Історії прив'язок» навіть через тижні синхронізацій: картка зберігає Offer ID і SEO, повертає старі ID постачальника, артикул, «Код товару Prom», назви/URL; ціна й наявність — з АКТУАЛЬНОЇ старої позиції у фіді (немає — «немає в наявності», остання відома ціна до наступної синхронізації; ціна з моменту прив'язки не відновлюється); відв'язана нова позиція — знову в черзі; якщо стара позиція була в черзі як нова — картка її забирає. Відмова з поясненням, якщо старий ID або старий код тепер у іншої картки або картку вже прив'язано новіше. Якщо під час активної прив'язки стара позиція знову з'явилась у фіді — попередження в «Історії прив'язок». Запобіжник: жоден ID постачальника не може належати двом карткам |
| Заморожені ID | не повертаються; у чергу — лише за сильного збігу (артикул + обидві назви) з товаром, чий ID зник із фіду, з позначкою «(ID у «Заморожених ID»)» |
| Пошкоджений/неповний XML | нічого не пишеться: помилка розбору; обсяг < max(4157, 80% попереднього); застарілий фід; зникло > max(50, 2%) товарів; «немає в наявності» або «в наявності» стало > max(50, 2%) товарів |

## 8. «Журнал» і заблоковані оновлення (22.10.2026)

- Формат як у mtUpdate: значення наявності «+» / «-» без апострофів. Захист від формул — режим запису RAW (Google не розбирає вміст: «=…» від постачальника зберігається як текст).
- Заблоковане оновлення (масова зміна наявності, масове зникнення, неповний / застарілий / пошкоджений XML, зміни поза затвердженням, конфлікт ID постачальника) → у таблиці змінюється ЛИШЕ «Журнал»: один рядок [час, «СИСТЕМА», —, «ОНОВЛЕННЯ ЗАБЛОКОВАНО», тип, «зачеплено N; поріг M», причина]. Ціни, наявність, SEO, каталог і черга не змінюються.
- Якщо записати подію в «Журнал» не вдалося — таблиця не змінюється зовсім, а тип, кількість, поріг і причина лишаються у звіті запуску (журнал GitHub Actions, без секретів і товарних ID).

## 9. Знижка, підказка прив'язки, нетоварні записи (22.10.2026, локально)

- **Знижка** — як у mtUpdate: у клітинку пишеться ЧИСЛО 0.2, а колонці «Знижка» (каталог і черга) ставиться формат «0%» (Google показує «20%»). Так само в «Журналі»: «було/стало» для знижки — числа (0.2 ↔ порожньо). Формули цін і план (порт mtPlan) не змінені: перетворення «20%» → 0.2 лише на запису. Повторний запуск не вважає 0.2 і «20%» зміною. YML: 0.2 дає той самий offer, що й «20%».
- **«ПРИВ'ЯЗАТИ ДО»** підказується лише тоді, коли схожа картка основного каталогу справді зникла з фіду. Якщо стара позиція знову є у постачальника — підказки немає; у «Перевірці» лишаються «МОЖЛИВИЙ ДУБЛЬ», причина збігу й примітка, що стара картка знову у фіді. Автоматичного видалення, затвердження чи прив'язки немає.
- **Нетоварні записи** (напр. «Співпраця по дропшипінгу»): у «Перевірці» на початку — «НЕТОВАРНИЙ ЗАПИС (причина) — не товар; рішення за вами». Джерела: аркуш «Аудит» (лише читання; позначка НЕТОВАРН… у «Тип» або «Причина») або ознаки (порожній артикул + назва про співпрацю / дропшипінг / послуги). Лише позначка: запис лишається в черзі.

## 10. «Сторож новинок» і сирі дані черги (22.10.2026, локально; погоджено власником)

**Новинки.**
- Новий ID у фіді постачальника — спершу **кандидат** у Cloudflare Worker. У чергу він не потрапляє одразу.
- Worker запам'ятовує перше виявлення й останню суттєву зміну (назви UA/RU, артикул, URL, фото, характеристики).
  Будь-яка зміна запускає 10 хв стабільності заново.
- Лише після ≥10 хв без змін і повних даних (назви UA і RU, артикул, ціна > 0, UAH, наявність, ≥1 фото, ≥1 характеристика)
  кандидат передається в GitHub intake (`copy-intake`).
- Intake повторно перевіряє його за ПОВНИМ XML: стабільність, той самий відбиток, повнота. Лише тоді додає в «Нові товари».
- «Виявлено» — час першого виявлення Worker. «Остання зміна постачальника» — остання суттєва зміна.
- Дата `yml_catalog` не є ознакою змін. У Prom це час генерації фіду: 21:06 → 21:13 між сусідніми запусками без змін асортименту.
  Чи змінюється вона саме від редагування картки, не перевірялось — на неї не покладаємось.

**Синхронізація кожні 4 год НЕ додає новинок.**
- Якщо Worker, KV чи GitHub intake недоступні, новинки лишаються кандидатами.
- Ціни й наявність затверджених товарів оновлюються як завжди.

**Сирі дані незатверджених позицій (варіант А).**
- Під час синхронізації та intake із XML оновлюються:
  - «Назва постачальника UA/RU», «Артикул постачальника», «URL постачальника»;
  - «Фото JSON», «Характеристики JSON»;
  - ціни й наявність.
- SEO-поля (Назва UA/RU, Опис UA/RU, Запити UA/RU) **не перезаписуються ніколи**.
- Кожна зміна пишеться в «Журнал» (поле, було / стало). Для опису постачальника — SHA і довжина.
- Нові колонки черги додаються автоматично один раз: «Остання зміна постачальника», «SHA даних постачальника»,
  «Погоджено для SHA», «SHA SEO при додаванні».

**Повторна перевірка.**
- SEO вважається початим, якщо:
  - SEO-поля відрізняються від записаних при додаванні; або
  - стоїть рішення; або
  - у рядку з черги до запуску контролю назви вже відрізняються від назв постачальника.
- Якщо після цього змінюються суттєві дані постачальника, з'являється «ПОТРЕБУЄ ПОВТОРНОЇ ПЕРЕВІРКИ (змінено: …;
  різниця комплектації: …)», і затвердження блокується.
- Власник ставить «ПЕРЕВІРЕНО» (або «ПЕРЕВІРЕНО <SHA>»). Підтвердження прив'язується до SHA, **записаної в рядку**, —
  саме ці дані бачив власник, а не свіжі з XML.
- Якщо постачальник змінив дані до цього запуску або пізніше, підтвердження недійсне, і знову потрібна перевірка.
  Вказана SHA, що не відповідає поточній, — не приймається.

**Дублі** — за актуальними даними: спершу оновлюються сирі дані черги, потім рахується схожість.

**Захисти.**
- Повторний intake без дублів («ВЖЕ Є»).
- Підтвердження загубилось — Worker повторює через 60 хв.
- Відмова intake — пауза 30 хв.
- Не більше 12 запусків GitHub на добу UTC і не частіше разу на 15 хв.
- Чергу редагують під час intake — нічого не записано.
- copy-sync і copy-intake — одна група паралельності GitHub.
- Ні Worker, ні workflow не передають ID товарів у журнали GitHub.

| KV: читання | 100 тис./добу | ≈580/добу | — |

Чи обмежує Prom частоту завантажень — невідомо. На HTTP 429/503 Worker робить паузу 30 хв.

**CPU Worker — НЕ вкладається з резервом на локальному вимірюванні.**
- Реальний фід, 5230 offer: operational ≈11 мс, medium ≈14 мс на крок. Ліміт — 10 мс, мета з резервом — ≤7 мс.
- Потрібне вимірювання в Cloudflare до будь-якого розкладу.
- Запасні варіанти (безкоштовні):
  - **(а)** `operational` + двофазна перевірка фото / характеристик у GitHub (реалізовано). Друга фаза ≥10 хв, ≈2 запуски GitHub на новинку.
  - **(б)** Apps Script в **окремому** Google-акаунті: власна квота 90 хв/добу, не зачіпає живий mtUpdate; інтервал 10 хв.
    Не реалізовано; потрібне рішення власника.
  - **(в)** Рідше: GitHub schedule кожні 2 год (≈360 хв/міс) — вкладається в резерв, але затримка до ~2 год.

## 11. «Сторож новинок» на SQLite Durable Object (23.10.2026, лише локально; погоджено власником)

**Причина.** Вимір 22.10 у Cloudflare: звичайний Worker Free (10 мс CPU) не вкладається — повний цикл 66 мс.
За документацією DO має 30 с CPU на виклик, зокрема на alarm; чи це діє на Free — перевірить один ручний тест.

**Що змінилось.**
- Вхідний Worker лише маршрутизує (ключ доступу → DO «main»). Вся робота й стан — у SQLite Durable Object.
- Автоматичні перевірки — alarm DO кожні 5 хв. Cron Triggers не потрібні.
- Розклад вимкнено подвійно: без змінної `ALARMS_ALLOWED="yes"` при розгортанні `POST /schedule` відхиляється.
- Варіант зі сховищем KV прибрано: дубля механізму немає.
- Бізнес-логіка без змін: те саме ядро `src/core/intake.mjs` і той самий GitHub intake.
  Контрольні суми DO = старий Worker = GitHub intake (тести: синтетика 5300 товарів і реальний знімок фіду).

**Надійність.**
- Одна «оренда» запуску: паралельні цикли неможливі, після збою оренда спливає за 5 хв.
- Повторний alarm (доставка «щонайменше раз») < 4 хв після циклу — пропуск. Наступний alarm ставиться до циклу.
  Помилки назовні не кидаються, тож немає нескінченних повторів.
- Стан читається вже після завантаження фіду, синхронно, без await до запису: звіт GitHub, що прийшов під час
  завантаження, не губиться.
- Запис — лише змінених рядків і однією транзакцією.
- 429/503 — пауза 30 хв. GitHub недоступний — пауза 15 хв, запуск не зараховано.
- Переадресації заборонені. Адреса фіду — лише Market Tools.
- Пошкоджений, обірваний або з повтором ID фід — стан без змін.
- DO не має доступу до Google Sheets. Новинки — лише через GitHub intake у «Нові товари».
- Синхронізація цін і наявності від DO не залежить.

**Квоти Free (288 перевірок/добу).**
- Запити — ≈0,3%.
- Тривалість — ≈4,5% (≈590 GB-s).
- Прочитані рядки — 0,2–0,5%; записані — 1,5–1,9%.
- Сховище < 1 МБ.
- CPU 66 мс із 30 с.

**Ризики, які перевіряються лише в Cloudflare.**
- CPU-ліміт Free для DO: 30 с чи 10 мс.
- Чи «засинає» DO між alarm. Якщо ні, тривалість зростає до ≈83% — більше за ліміт із резервом.

## 12. Остаточні правила оновлення товарів у черзі (погоджено 23.10.2026, лише локально)

**Ціна й наявність — завжди автоматично.**
- Оновлюються за погодженими формулами в синхронізації та intake: без попереджень, без ручного підтвердження, незалежно від стану SEO.
- Не входять у SHA даних постачальника, тож не скидають «ПЕРЕВІРЕНО» і не створюють попереджень.
- Зник із повного коректного XML → «немає в наявності». Пошкоджений або неповний XML → масові оновлення заблоковано (як і раніше).

**Сире SEO** (ми не редагували).
- Визначається лише за знімком: «SHA SEO при додаванні» — контрольна сума SEO-полів, яку записала сама система (при додаванні й при кожному автооновленні).
- Різниця з поточними даними постачальника НЕ означає «власне».
- Зміна назв / опису / моделі постачальника → SEO-копії оновлюються автоматично, без попереджень; знімок рухається разом із копією.

**Власне SEO** (SEO-поля ≠ знімку системи, або стоїть рішення власника).
- Назви UA/RU, описи, пошукові запити ніколи не перезаписуються.
- Суттєва зміна даних постачальника (назви, артикул, модель, URL, фото, характеристики, опис) → «ПОТРЕБУЄ ПОВТОРНОЇ ПЕРЕВІРКИ» з «було → стало».
- Порівнюються попередні й нові дані ПОСТАЧАЛЬНИКА: знімок «Погоджені дані постачальника» — 5-та службова колонка. Наше SEO з ними не порівнюється.

**«ПЕРЕВІРЕНО».**
- Прив'язується до SHA, записаної в рядку (дані, які бачив власник). Наступна суттєва зміна — знову перевірка; ціна й наявність — ні.
- Поки є попередження, затвердження заблоковане. Ціни й наявність при цьому оновлюються.

**Рядки до запуску контролю (без знімка).**
- Сире SEO лише якщо назви = назвам постачальника, запитів немає й опис = поточному опису постачальника.
- Назви відрізняються → власне (не перезаписується).
- Опис постачальника відтоді змінився → «походження SEO невідоме»: SEO не змінюється, затвердження заблоковане. Команди:
  - «SEO ПОСТАЧАЛЬНИКА» — підтвердити копію, далі автооновлення;
  - «ПЕРЕВІРЕНО» — підтвердити власне.

## 13. Оновлення даних постачальника під тим самим ID (погоджено 23.10.2026, лише локально)

Постачальник під тим самим ID змінив модель, артикул, назви чи інші дані → нові дані приймаються автоматично. Синхронізацію й імпорт така зміна не блокує. Діє для обох аркушів.

**«Основний каталог».**
- Автоматично оновлюються: «Назва постачальника UA/RU», «Артикул постачальника», URL постачальника, «Модель», «Фото JSON», «Характеристики постачальника JSON» (сирі). Підготовлені «Характеристики JSON» — лише за схемою категорії (розділ 14). Печатка рядка перераховується.
- Ціна й наявність — автоматично за погодженими формулами. «ЗМІНА_ІДЕНТИЧНОСТІ» більше не зупиняє оновлення цін: перед звіркою сирі поля оновлюються, тож ідентичність збігається.
- Наше SEO (назви UA/RU, описи, пошукові запити) не змінюється. У «Журнал» додається запис «ПОТРЕБУЄ ПОВТОРНОЇ ПЕРЕВІРКИ» з «було → стало» і поміткою «ІНФОРМАЦІЙНО: наше SEO не змінено». Цей запис нічого не блокує.
- «Код товару Prom» іде за новим артикулом, лише якщо код був порожній або дорівнював старому артикулу і новий артикул не зайнятий іншою карткою. Інакше код не змінюється, а в «Журналі» з'являється «НЕ ЗМІНЕНО: артикул … уже має товар …».
- Offer ID Prom не змінюється ніколи. Зміна ID постачальника — як і раніше, лише ручна прив'язка («ПРИВ'ЯЗАТИ ДО»).
- «Опис UA/RU» (наше SEO) і «Виробник» основного каталогу не оновлюються. Оригінальний опис постачальника — в окремих колонках (розділ 14).

**«Нові товари».**
- Як у розділі 12. «Модель» тепер теж сирі дані: оновлюється завжди, навіть за власного SEO.
- Сире SEO оновлюється з постачальником. Власне SEO зберігається; суттєва зміна дає «ПОТРЕБУЄ ПОВТОРНОЇ ПЕРЕВІРКИ». Попередження інформаційне: не блокує ні оновлення, ні синхронізацію, ні імпорт, ні ручне «ЗАТВЕРДЖЕНО» (уточнення власника 23.10.2026, розділ 14; «ПЕРЕВІРЕНО» лише знімає попередження).

**Фото (обидва аркуші).**
- Список фото замінюється повністю поточним списком постачальника: додані, видалені, замінені, порядок, головне фото.
- Джерело — лише повний XML. У полегшеному (операційному) XML фото немає. Ця відсутність не означає команди видалити фото.
- Порожній список фото з повного XML не стирає наявні («у повному XML немає фото — залишено попередні»).
- Повний XML недоступний або неповний (менше 95% потрібних позицій) → фото й характеристики не оновлюються, лише попередження. Решта синхронізації працює.

**Захист від пошкоджених даних (як і раніше, плюс нове).**
- Пошкоджений або неповний XML і масова зміна наявності / зникнення → оновлення заблоковано.
- Нове: назви чи артикул змінилися більш ніж у max(50, 2%) карток → «МАСОВА ЗМІНА ДАНИХ ПОСТАЧАЛЬНИКА». Фото змінилися більш ніж у max(200, 10%) карток → «МАСОВА ЗМІНА ФОТО». В обох випадках синхронізацію заблоковано й записано в «Журнал».

**Відмінність від LIVE mtUpdate (свідома).** LIVE за зміни назв / артикулу ставить «ЗМІНА_ІДЕНТИЧНОСТІ» і не оновлює ціни. Нова система спершу приймає сирі дані постачальника. Саму функцію звірки (planRows) не змінено, тож паритет на незмінних даних зберігається.

## 14. Характеристики Prom і категорії (погоджено 23.10.2026, лише локально)

**Колонки (обидва аркуші, у кінці; додаються автоматично; не входять у печатку).**
- «Характеристики постачальника JSON» — сирі характеристики XML, оновлюються автоматично лише з повного XML (порожній список не стирає).
- «Опис постачальника UA» / «Опис постачальника RU» — оригінальний опис постачальника (відновлення й перенесення характеристик).
- «Походження характеристик JSON» — для кожного запису: джерело (XML / ОПИС / XML БЕЗ ЗІСТАВЛЕННЯ / ВРУЧНУ / НЕВІДОМО), id атрибута Prom; приховані власником поля; примітки й конфлікти.
- «Категорія Prom: підтверджено» — «PROM <дата експорту>».
- «Характеристики JSON» — підготовлені для Prom (саме вони йдуть у YML, як і раніше).
- SHA даних постачальника й відбитки «Сторожа новинок» рахуються за СИРИМИ характеристиками.

**Схеми** — `schemas/prom/<categoryId>.xml` (точно як надав власник), `MANIFEST.json` (SHA256), `units.json` (погоджені перерахунки одиниць; зараз порожньо), `mapping/<categoryId>.json` (погоджені синоніми назв і значень). Файл зі зміненою SHA або з помилками структури не використовується. Одна категорія з різним вмістом в отриманих файлах → «КОНФЛІКТ», не імпортується. Імпорт: `node tools/prom-schemas.mjs import <файли>`, перевірка: `node tools/prom-schemas.mjs check`. Зараз 18 схем (з них 2 порожні «…, загальне»).

**Перенесення в поле Prom** — лише при підтвердженій відповідності:
- назва — точна назва атрибута ЦІЄЇ категорії (UK або RU) або погоджений синонім; схожості назв недостатньо (потужність двигуна ≠ споживана потужність);
- real / integer — одне число, одиниця точно як у схемі (UK або RU) або погоджений перерахунок, у межах min / max; без одиниці — не заповнюється; integer — ціле;
- bool — лише так / ні (так, є, да / ні, немає, нет);
- singleselect — точний допустимий варіант (UK або RU) або погоджений синонім значення; у поле пишеться UA-назва варіанта;
- multiselect — автоматично не заповнюється (формат передачі кількох значень у YML не підтверджено); free — текст до 255 символів.
- Пріоритет: XML → опис → наші ручні виправлення (мають перевагу над будь-яким автоматичним значенням). Конфлікт XML і опису — береться XML, опис не чиститься. Кілька різних значень — поле не заповнюється.

**Збереження підготовленого.**
- Записи, які система не може достовірно пояснити (НЕВІДОМО), зберігаються як є; поки такі є, незіставлені сирі характеристики не додаються (щоб не задублювати підготовлене).
- Правку власника система розпізнає (запису немає серед того, що вона писала) — далі це ВРУЧНУ: не перезаписується; відмінність від постачальника — примітка. Прибране власником автоматичне поле не повертається.
- Автоматичні поля (XML / ОПИС) і дослівні сирі характеристики оновлюються й прибираються разом із постачальником.
- Основний каталог без схеми категорії — підготовлені характеристики не змінюються. Черга без схеми — копія сирих, як раніше.
- Незіставлені характеристики XML — як і раніше, окремими характеристиками (не полями Prom). Незіставлене з опису лишається в описі.

**Опис.** Пари «назва — значення» беруться лише з рядків таблиць із двома клітинками й рядків «Назва: значення». Очищення — лише СИРОЇ копії опису в черзі (SEO не редагували) і лише від перенесених пар; оригінал зберігається; власний SEO-опис не чиститься ніколи. Вмикається окремо: `config.characteristics.cleanDescriptions = true` (за замовчуванням вимкнено — до перевірки на тестовій копії).

**Захист.** Підготовлені характеристики змінились би більше ніж у max(200, 10%) карток основного каталогу → у цьому запуску не застосовуються (попередження й запис у «Журналі»), сирі дані, ціни й наявність оновлюються. Перше застосування схем — окремим погодженим запуском (`config.characteristics.maxChangedRows`).

**Категорія Prom — джерело істини** (`src/core/prom-categories.mjs`).
- Категорія з експорту Prom має пріоритет над таблицею; постачальник категорію не задає (у його XML її немає), синхронізація її не змінює.
- Не повертаємо стару: старіший експорт не перекриває новішого підтвердження. Невідома (немає в експорті / порожня / повтор товару) — не вигадується й не змінюється.
- Після зміни категорії — нові ID і посилання, печатка, запис у «Журналі»; характеристики перебудовуються за схемою нової категорії; YML віддає нову portal_category_id.
- Застосування до тестової копії — окремим погодженим кроком на АКТУАЛЬНОМУ експорті Prom (експорт 21.10 може бути застарілим); паспорт каталогу оновлюється в тому самому записі.

**Сухий прогін на локальних даних (21.10, лише читання).** Основний каталог 5029; категорія з Prom відрізняється у 282; схеми покривають 1774 картки. Підготовлені характеристики змінились би в 896 (> поріг 512 — перше застосування буде відкладено захистом). Додано 2270 полів Prom (2114 з опису, 152 з XML). 143 дослівні сирі записи перетворено точно в те саме поле Prom, 2 — дублікати сирого параметра, значення яких уже є в полі. Втрачених підготовлених значень — 0. Невизначеного походження — 169 записів у 83 картках (збережено).

**Схеми від власника (23.10.2026, лише локально).** Отримано 28 фрагментів; збережено дослівно в «Матеріали / Схеми Prom / 2026-10-23» (фрагмент-NN.xml). Належність атрибутів — лише за `<category id>` блоку. Імпортовано 27 (тепер 45 схем). Не імпортовано 12110201 — фрагмент обірвано (немає `</category>`). Не отримано 190402 і 14200377.
