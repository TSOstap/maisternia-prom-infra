## C2 детально (рекомендований перший крок із реальними даними)

**Варіант A — без жодних прав доступу.** Власник у робочій таблиці відкриває Файл → Завантажити → Microsoft Excel (.xlsx) і кладе файл у `E:\Prom Maisternia Market\Матеріали` (правило R-MAT, RULES.md). Дія лише читає таблицю.

Claude:

1. додає локальний конвертер xlsx → знімок (як `*.inspect.ndjson` у Codex). Знадобиться бібліотека читання xlsx (exceljs, як у Codex) — нова залежність, лише в інструменті;
2. запускає `tools/snapshot-parity.mjs`. Очікування: 0 невідповідностей печаток; count/idsSha/groupsSha = LIVE MTY; contentSha = LIVE `e2871d9e…`; YML ідентичний LIVE;
3. окремо порівнює «Нові товари» з паспортом 92 від Codex (лише читання);
4. реальні дані не комітяться і зберігаються лише поза репозиторієм.

Застереження: типи клітинок у xlsx-експорті можуть відрізнятися від `getValues()` (дати, числа як текст). Розбіжність печаток у варіанті A ще не означає помилку системи — тоді переходимо до варіанта B.

**Варіант B — Sheets API (цільовий для автоматизації).**

1. Проєкт Google Cloud **без billing account**. Увімкнений Sheets API, service account.
2. Таблицю поділено на email service account з правом **Viewer**. Це зміна прав доступу до робочої книги, тому потрібне окреме погодження. Viewer не може нічого змінити.
3. Адаптер `GoogleSheetsCatalogSource`: `values.batchGet` порціями (≤2 МБ на запит), експоненційний backoff на 429. Режим `valueRenderOption=UNFORMATTED_VALUE` — найближчий до `getValues()`. Обробку дат треба підтвердити звіркою печаток. ≈20–30 запитів на запуск при квоті 300/хв.
4. Ключ service account як GitHub Secret або, краще, Workload Identity Federation без довгоживучого ключа. Спосіб вибирається на цьому етапі за документацією Google.

## C3 детально

- Bucket `maisternia-feeds` (Standard). Без public access, без r2.dev, без custom domain.
- R2 API token: Object Read & Write лише на цей bucket. Він потрібен для S3-адаптера в Actions.
- Адаптер `R2ObjectStore` з контрактом `LocalObjectStore`: put/head/getBuffer/getStream/list/delete. Реалізація — через `@aws-sdk/client-s3` (документований Cloudflare шлях для R2) або власний SigV4. Ті самі тести `test/pipeline.test.mjs` проганяються проти тестового bucket (contract tests).
- Worker деплоїться з `worker/wrangler.example.jsonc` під тестовою назвою. Секрет `FEED_ACCESS_KEY` — `wrangler secret put`. Перевірки: 403 без ключа, потік 50 МБ, HEAD, fallback на previous, CPU-час у логах (НЕОДНОЗНАЧНО в документації — виміряти).
- Моніторинг квот: токен Account Analytics Read → щоденний GraphQL-запит `r2OperationsAdaptiveGroups` / `r2StorageAdaptiveGroups` → `usage/`, STOP розкладу на 80%.

## C4 детально (shadow)

- `update.yml`: cron `17 */4 * * *`. Prom оновлює ключові поля раз на 4 год у межах 6:00–22:00, точний час кабінету невідомий.
- Звіт розбіжностей на кожен запуск:
  - F:M, які обчислила нова система, проти F:M у знімку таблиці після найближчого mtUpdate;
  - статуси зіставлення;
  - склад фіду (idsSha) і, за наявності доступу, count/idsSha чинного YML.
- Політика для R1/R2 (рішення D1) застосовується лише після погодження. До того — паритет.

## Відкат на будь-якому етапі

Етапи C1–C5 нічого не змінюють у магазині, тому відкат — просто зупинити workflow. Після C6 відкат — повернути в Prom старе посилання /exec: Apps Script увесь цей час продовжує формувати фід. Нова система не видаляє і не змінює жодного ресурсу старої.
