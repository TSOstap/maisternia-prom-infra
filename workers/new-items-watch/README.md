# «Сторож новинок» — Cloudflare Free, SQLite Durable Object

**Статус (23.10.2026): лише локально.** НЕ розгорнуто. Durable Object не створено. Alarms і Cron не ввімкнено. Секретів немає.
Тестовий Worker `mm-new-items-watch-test` (вимір CPU 22.10) лишається в Cloudflare без змін.

## Навіщо Durable Object
Вимір 22.10 у Cloudflare показав: звичайний Worker Free (10 мс CPU на виклик) не вкладається.
Повний цикл на реальному фіді — **66 мс CPU**, а сам виклик без XML — 10,6 мс.
За документацією Durable Object має **30 с CPU на виклик**, зокрема на alarm.
Застереження: та сама документація каже «Workers Limits apply according to your Workers plan». Чи діє на Free 30 с,
чи 10 мс, остаточно покаже лише один ручний тест (див. нижче).

## Архітектура
```
Вхідний Worker (src/index.mjs → router.mjs): лише ключ доступу і маршрут → DO «main»
SQLite Durable Object (watch-do.mjs → watch-core.mjs):
  alarm кожні 5 хв (вимкнено) або POST /run (ручний цикл)
    1. оренда запуску (паралельні цикли неможливі; після збою спливає за 5 хв)
    2. завантаження фіду (src/cycle.mjs): лише https://market-tools.com.ua/, redirect «manual», 3xx — помилка, 429/503 — пауза 30 хв
    3. СИНХРОННО, без await: читання стану з SQLite → розбір (src/core/intake.mjs) → план → запис різниці однією транзакцією
    4. якщо є готові — запуск GitHub intake (без ID; недоступний — пауза 15 хв, запуск не зараховано)
GitHub intake (як і раніше): GET /intake → повторна перевірка за повним XML → «Нові товари» → POST /ack
```
Ядро правил — спільне з GitHub intake (`src/core/intake.mjs`). Контрольні суми однакові: перевірено тестами
на синтетиці (5300 товарів) і на реальному знімку фіду.

## Сховище SQLite (`src/store.mjs`)
| Таблиця | Що зберігає |
|---|---|
| `meta(k, v)` | `known` — база відомих ID **одним рядком**; `dispatch` — ліміти GitHub; `backoffUntil`, `githubBackoffUntil`, `lastRun`, `lastDispatch` (стан очікування intake), `lastCycleAt`, `lease`, `schedule` |
| `candidates(id, rec)` | кандидати: перше виявлення, остання суттєва зміна, відбиток, чого бракує, статус, історія (останні 10) |
| `queue(id, rec)` | позиції «Нових товарів»: відбиток сирих даних і очікувана зміна |
| `events(seq, at, id, what)` | журнал важливих змін; зберігається 30 днів |

- Пишуться лише змінені рядки й лише в `transactionSync`: при збої — або все, або нічого.
- Після перезапуску чи виселення DO стан повністю в SQLite. В пам'яті лише прапорець «цикл іде».

## Ендпоінти (усі — з `Authorization: Bearer <WATCH_KEY>`)
| Шлях | Дія |
|---|---|
| `GET /status` | кандидати, статуси, розклад, час наступного alarm, паузи, останні події |
| `GET /intake` | список готових кандидатів для GitHub intake |
| `POST /ack` | звіт GitHub (база відомих ID, відбитки черги, результати) |
| `POST /run` | один ручний цикл (для тесту) |
| `POST /schedule` | `{"on": true}` — лише якщо при розгортанні задано `ALARMS_ALLOWED="yes"` (зараз немає) |

## Безкоштовні квоти (DO Free, 288 перевірок/добу; ліміти — з документації Cloudflare)
| Ресурс | Ліміт Free | Оцінка | Частка |
|---|---|---|---|
| Запити DO | 100 тис./добу | ≈ 290–340 | 0,3% |
| Тривалість | 13 000 GB-s/добу (реальний час × 128 МБ) | ≈ 288 × 16,3 с × 0,125 ГБ ≈ 590 GB-s | **≈ 4,5%** (ризик — див. нижче) |
| Прочитані рядки SQLite | 5 млн/добу | 8–23 тис. (симуляція доби) | 0,2–0,5% |
| Записані рядки SQLite | 100 тис./добу | 1,5–1,9 тис. (разом із setAlarm) | 1,5–1,9% |
| Сховище | 5 ГБ | < 1 МБ | ≈ 0% |
| CPU | 30 с на виклик (застосовність на Free — перевірити) | 66 мс (вимір 22.10) | 0,2% |
| Пам'ять | 128 МБ на ізолят | 19 МБ (вимір 22.10) | 15% |
| Підзапити | 50 на виклик | ≤ 2 | 4% |
| GitHub Actions | 2000 хв/міс | ≤ 12 запусків/добу → разом із синхронізацією 38–60% | ≤ 60% |

**Ризик тривалості.** Тривалість рахується, поки DO працює або «простоює в пам'яті без можливості hibernate».
- Якщо DO не засинатиме між alarm, оцінка — до 24 год × 0,125 ГБ ≈ 10 800 GB-s, тобто 83%. Це більше за ліміт із резервом.
- Перевірити це можна лише в Cloudflare, метрикою тривалості DO під час ручного тесту.

## Один майбутній ручний тест у Cloudflare Free (НЕ виконано; лише після окремого погодження)
1. Push і CI.
2. Розгорнути з окремою назвою: `mm-new-items-watch-do-test`, `--name`.
   - Без `ALARMS_ALLOWED`, без `GITHUB_TOKEN`.
   - Створюється DO-клас `WatchDO` (SQLite, Free).
3. Секрети (`wrangler secret put`, значення не виводяться):
   - `WATCH_KEY` — згенерувати локально, зберігати поза репозиторієм;
   - `SUPPLIER_FEED_URL` — з `Вигрузки.docx`.
4. `POST /ack` з базою відомих ID (локальний знімок) — щоб частина ID стала кандидатами, як у тестах.
5. **Рівно один** `POST /run`. Перевірити:
   - CPU, тривалість і пам'ять DO в аналітиці Cloudflare;
   - кандидати та їхні відбитки = локальні;
   - відсутність 429/503;
   - що Cloudflare не обірвав виклик (CPU-ліміт Free для DO).
6. Через 10–15 хв ще раз подивитися метрику тривалості DO — чи DO «заснув» (ризик тривалості).
7. Нічого не вмикати автоматично. Після звіту — рішення власника: залишити, видалити або перейти до alarm.

Перевірка локально: `npm test`. Реальний знімок фіду: `MM_REAL_FEED=<шлях до XML> node --test test/watch-do.test.mjs`.
