# «Сторож новинок» — Cloudflare Worker (Workers Free)

**Статус: код і тести готові локально. НЕ РОЗГОРНУТО. Розклад вимкнено (`"crons": []`).** Розгортання, KV, секрети й розклад — лише з окремого погодження власника.

## Що робить
1. За розкладом (план: кожні 5 хв) завантажує фід постачальника — ту саму адресу, що TOOLS_FEED_URL, у профілі
   `medium` (без описів і ключових слів) або `operational` (лише назви, артикул, ціни — запасний профіль для CPU).
2. Нові ID (яких немає в базі відомих) стають **кандидатами**. Worker запам'ятовує перше виявлення й останню суттєву зміну.
3. Суттєві поля: назви UA/RU, артикул, URL, фото, характеристики. Будь-яка зміна запускає 10-хвилинний відлік заново.
   Дата `yml_catalog` не використовується (у Prom це час генерації фіду).
4. Лише після ≥10 хв без змін і повних даних кандидат «ГОТОВИЙ». Тоді Worker запускає GitHub workflow `sheets-verify.yml`
   у режимі `copy-intake`. У запуску **немає ID товарів**: список GitHub бере за ключем із `GET /intake`.
5. GitHub intake повторно перевіряє кожного кандидата за повним XML (стабільність, відбиток, повнота) і додає його в
   «Нові товари». Потім надсилає звіт у `POST /ack`.

У Google-таблицю Worker не пише нічого. В основний каталог і YML нічого не потрапляє без затвердження власника.

## Ендпоінти (усі — лише з `Authorization: Bearer <WATCH_KEY>`)
| Шлях | Що повертає / робить |
|---|---|
| `GET /status` | Стан для перегляду: кандидати, статуси, чого бракує, історія змін, ліміти запусків |
| `GET /intake` | Останній список готових кандидатів (для GitHub intake) |
| `POST /ack` | Звіт GitHub: база відомих ID, відбитки черги, результати («ДОДАНО» / «ВЖЕ Є» / «ВІДМОВА») |

## Стан і безкоштовні ліміти
- KV `watch:v1` — стан, пише **лише cron**. KV `ack:latest` — звіти GitHub, пише лише `/ack`.
  Двох записувачів одного ключа немає, бо KV не має транзакцій.
- Записи в KV — лише при змінах або раз на годину. Ліміт Free — 1000 записів/добу.
- Запуски GitHub — не більше 12 на добу UTC і не частіше разу на 15 хв. Повтор, якщо немає підтвердження, — через 60 хв.
  Після відмови intake — пауза 30 хв.
- HTTP 429/503 від постачальника — пауза 30 хв без завантажень.
- Неповний фід (< max(4157, 80% попереднього)) — нічого не вирішується.

## CPU (головний ризик) — виміряно локально 22.10.2026 на реальному фіді (5230 offer)
| Профіль | Розмір | Крок Worker (медіана, локальний ПК) |
|---|---|---|
| operational | 4,9 МБ | ≈ 11 мс (декодування 3,1 + скан 5,8 + план 1,7) |
| medium | ≈ 8,3 МБ | ≈ 14 мс |

Ліміт Workers Free — **10 мс CPU** на виклик. Мета з резервом 30% — ≤ 7 мс.
**На локальному ПК не вкладається.** Реальні процесори Cloudflare інші, тож рішення — лише після вимірювання
в Cloudflare (тестове розгортання в режимі спостереження). Запасні варіанти — `S1-PLAN.md`, розділ 10.

## Розгортання (НЕ виконано; лише після погодження)
1. Власник: створити простір KV і вписати його ID у `wrangler.jsonc`.
2. Власник: додати секрети (`wrangler secret put`): `SUPPLIER_FEED_URL`, `WATCH_KEY`. `GITHUB_TOKEN` — пізніше,
   окремим кроком (fine-grained, лише цей репозиторій, право запускати workflow).
3. Розгорнути без розкладу й без `GITHUB_TOKEN` → виміряти CPU (`wrangler tail` / метрики).
4. Лише якщо CPU ≤ 7 мс: розклад `*/5 * * * *` (або `*/10`), спершу в режимі спостереження.
5. Потім — `GITHUB_TOKEN` і секрети `MM_WATCH_URL`, `MM_WATCH_KEY` у GitHub → intake лише в тестову копію.

Перевірка: `npm test` (`test/intake.test.mjs`, `test/intake-sim.test.mjs` — Worker наскрізно з KV у пам'яті).
