## Наскрізні сценарії (test/pipeline.test.mjs)

1. Перший запуск: синк OK → фід опубліковано → Worker віддає XML, SHA = ETag, ID звірено; лічильник usage оновлено.
2. Ціни без змін → `REUSED`, нового PUT немає.
3. Зміна ціни → нова версія, попередня збережена. Якщо активний об'єкт зник, Worker віддає previous. Відкат до зниклої версії відхиляється, до попередньої — успішний.
4. Обрізаний фід постачальника → синк ERROR, стан і маніфест не змінені.
5. Падіння кількості >20% → синк зупинено.
6. Товар зник у постачальника → «-», синк OK, фід ERROR (паритет R1), маніфест не створено.
7. Ручна правка контенту без QA → фід ERROR («змінено після QA»), попередня версія лишається.
8. Відмова сховища на readback → кандидата прибрано, активна версія не змінена.
9. Ротація: retain=2 → не більше 3 версій у сховищі.
10. gzip: `.xml` → 503, `.xml.gz` → розпакований вміст = перевірений знімок, стиснення > 2×.
11. Worker: 403 без ключа або з хибним ключем; 503 до першої публікації; 404 для невідомого фіду; 405 для POST; HEAD; status.
12. Нові товари: дата першої появи зберігається між запусками, `newSinceLastRun` обнуляється.
13. ID в main і queue одночасно → синк зупинено до будь-якого запису.
14. Три фіди (main / queue з погодженими ID / all): незалежні. Зіпсований паспорт queue не зачіпає main і all.

Сценарій «товар зник» у test/pipeline.test.mjs тепер перевіряє режим `block` (паритет LIVE). Поведінку D1 перевіряє test/d1.test.mjs.
