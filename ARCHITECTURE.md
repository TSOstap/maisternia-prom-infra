# Архітектура нової інфраструктури «Майстерня Маркет»

Стан: **прототип, shadow-режим**. Хмарних ресурсів не створено. Робочий магазин не змінювався. Оновлено 21.10.2026 (звірка зі свіжими даними, рішення D1 і D1b).

## 1. Висновок щодо запропонованої архітектури

Схема «Google Sheets → GitHub Actions + Node.js → R2 → Worker → Prom» **придатна**. Безплатніших і надійніших варіантів не знайдено (COSTS.md, розділ 4). Є три уточнення:

1. **Google Sheets не повинна зберігати весь контент після ~10 тис. товарів.** Зараз 5029 рядків займають ≈49 МБ тексту. 30 тис. рядків займуть ≈290 МБ. Документація Google неоднозначна: «up to 20 million cells or 100MB» (COSTS.md, E2). Пропозиція на погодження: таблиця лишається пультом керування (ID, статус, група, ціни, прапорці, печатка), а довгий контент (описи, характеристики, фото, запити) переходить у версіоноване сховище контенту. До 5121 товару — без змін.
2. **Розмір YML для 30 тис. ≈ 290 МБ** перевищує рекомендовані Prom 180 МБ. Рішення закладені в прототипі: gzip (Prom підтримує ZIP/GZIP, реальне стиснення ≈ 0,16–0,2 → ≈ 50–60 МБ) або кілька фідів (Prom дозволяє до 4 посилань). Яке з них приймає саме ваш кабінет, треба перевірити тестовим імпортом.
3. **Репозиторій — приватний.** Публічний дає безлімітні хвилини, але логи бачать усі залогінені користувачі GitHub. Прогноз приватного: 700–1150 хв/міс із 2000 безплатних.

## 2. Схема

```
                  ┌──────────────────────── GitHub Actions (cron "17 */4 * * *", concurrency=update) ─────────────────────────┐
 Market Tools ───►│ 1. потоковий розбір фіду (без описів)   ─┐                                                               │
 (секрет URL)     │ 2. знімок каталогу (Sheets API, read-only)│─► 3. план F:M ─► 4. state/operational.json (ОДИН запис = коміт) │
 Google Sheets ──►│                                          ─┘          │                                                    │
 (service acct,   │                                                      ├─► 5. для кожного фіду: формування YML потоком      │
  Viewer)         │                                                      │      → незалежна перевірка XML → PUT версії        │
                  │                                                      │      → readback SHA → PUT manifest.json (перемикання)│
                  │                                                      ├─► 6. звіт нових товарів                            │
                  │                                                      └─► 7. звіт запуску + usage/<місяць>.json (квоти)    │
                  └──────────────────────────────────────────────┬──────────────────────────────────────────────────────────────┘
                                                                 ▼
                              Cloudflare R2 (приватний bucket, без r2.dev)
                              feeds/<фід>/versions/*.xml[.gz]  (незмінні, ротація 7)
                              feeds/<фід>/manifest.json        {active, previous, history}
                              state/*, reports/*, runs/*, usage/*
                                                                 ▼
                              Cloudflare Worker  GET /feeds/<фід>.xml?key=…  → потік active (fallback previous, інакше 503)
                                                                 ▼
                                                     Prom.ua (імпорт за посиланням)
```

## 4. Ключові рішення

1. **Паритет понад усе.** Ядро — це порти LIVE-функцій. Тест `test/parity-apps-script.test.mjs` запускає справжній LIVE-код у VM і порівнює ціни на 40 000 векторах, розбір, зіставлення, план F:M, тексти помилок і YML **байт-у-байт** (SHA, байти, sourceDigest).
2. **Набір товарів як дані, а не код.** `approved/<фід>.json` = {count, idsSha, contentSha, groupsSha, ids}. Новий паспорт створюється командою `approve`. Видалення будь-якого ID без явного списку `--allow-remove` заборонене (`guards.maxRemovedWithoutApproval=0`). Для паритету на справжніх даних перший паспорт можна заповнити значеннями чинного MTY.
3. **Один атомарний запис = коміт.** Синхронізація фіксується одним PUT `state/operational.json`. Публікація — одним PUT `manifest.json`. Будь-яка відмова до цього запису не змінює того, що бачить Prom.
4. **Ізоляція фідів.** Збій одного фіду не скасовує синхронізацію і не зачіпає інших (як у дизайні NEW92 Codex). Модель підтримує `main`, `new92` (лише погоджені ID черги через `filterByManifest`) і `all` (5121 = main + погоджена черга). Це шлях до одного фіду після імпорту 92.
5. **Версії незмінні.** Ключ версії містить час і SHA, тому перезапис неможливий. Зберігаються `retainVersions` (7) версій плюс active/previous. Відкат `cli rollback` перемикає маніфест лише після повної перевірки цільової версії.
6. **Worker не рахує SHA на кожен запит**, як це робить doGet, бо на Free-плані CPU-ліміт 10 мс. Замість цього SHA записується в метадані об'єкта під час завантаження, публікатор робить повний readback до перемикання, а Worker звіряє розмір і SHA-метадані з маніфестом.
7. **Shadow-режим.** Операційні значення нова система тримає у власному `state/operational.json` і не пише в таблицю. Повернення до старої системи — нічого не вимикати: Apps Script продовжує працювати паралельно, а Prom дивиться на старе посилання, доки його окремо не переключать.
8. **Нові товари — лише звіт.** Звіт містить ID, артикул, назви, URL, ціну, наявність, дату першої появи і зниклих кандидатів. Автоматичного додавання у фід немає: нові товари проходять контент, QA і погодження (окремий процес Codex/Claude).

## 6. Рішення D1 — зникнення товарів із фіду постачальника (погоджено власником 21.10.2026)

Реалізовано в прототипі (`src/core/d1.mjs`, `src/core/identity.mjs`, політика `missingPolicy` у `src/core/yml.mjs`). Тести — `test/d1.test.mjs`. Перевірка на реальних даних — DATA-AUDIT-20261021.md.

| 9 | Недоступний, неповний або аномально малий фід — не масове видалення | Наявні перевірки LIVE (HTTP, структура, ≥4157 і ≥80% від попереднього, вік ≤48 год) плюс **нова**: якщо за один запуск «зникло» більше ніж max(50, 2% каталогу), фід вважається несправним. **Перевірено на реальних даних 21.10:**
- моделювання повного перевипуску ID — 5134 правильні перев'язки, 0 хибних, 15 на ручну перевірку;
- shadow-прогін: 3 зникнення + 5 перевипусків → фід опубліковано, 3 «немає в наявності», 5/5 правильних перев'язок, 0 «нових» дублів.

**«Заморожені ID» (виправлення 22.10.2026):** offer, чий ID є в аркуші «Заморожені ID» (`config.catalog.knownIdSheets`), — свідомо виключений товар. Його не вважаємо «новим» і не ставимо в ручну чергу через схожість із живою карткою (комплект, слабкі ознаки). Виняток: якщо він схожий на картку, чий ID зник із фіду (сирота), — він іде в ручну чергу з позначкою `frozen: true`, бо це може бути новий ID того самого товару. Автоматично до замороженого offer нічого не прив’язується, статуси й «Заморожені ID» не змінюються. Звіт: `identity.frozenInFeed / frozenIgnored / frozenFlagged`. Тести — `test/frozen-identity.test.mjs`.

**Синоніми брендів (погоджено 22.10.2026):** `BRAND_SYNONYMS` у `src/core/identity.mjs` — Felső→Felso (основне), Kärcher=Karcher, Кентавр=Kentavr, Phiolent=Фиолент, Makita Corporation=Makita. Діє лише на порівняння брендів (ідентичність, звірки); бренди в картках, таблиці й фіді не перезаписуються. Нові синоніми — лише з офіційним джерелом і погодженням.

**Відомі межі:**
- GTIN у каталозі та у фіді постачальника відсутній, тому другого незалежного ключа немає;
- vendor/model читаються з фіду, якщо постачальник їх передає в операційному режимі. Це **НЕ ПЕРЕВІРЕНО** на живому фіді. Без бренду перевірка спирається на артикул і назви;
- поріг аномалії max(50, 2%) — початкове значення, його треба відкалібрувати на журналі змін за кілька тижнів shadow-роботи;
- кілька постачальників: зараз синк один, тому збій фіду постачальника зупиняє оновлення всіх фідів, а не лише «його» товарів. Для кількох постачальників потрібен окремий синк на постачальника. Це наступний крок архітектури.

### 6.1 Рішення D1b — конфлікт однієї картки (погоджено власником 21.10.2026)

Принцип: конфлікт одного товару не блокує оновлення всього YML. Реалізація: `policy.conflict = "isolate"` (`src/core/d1.mjs`, `src/core/yml.mjs`), тести — `test/d1b.test.mjs`. Режим `"block"` = чинна поведінка LIVE.

| П. | Вимога власника | Як реалізовано |
|---|---|---|
| 1 | Конфлікт ідентифікації, артикула, моделі, ціни або валюти — ізолювати лише цю картку | Статуси mtMatch: КОНФЛІКТ_ID, КОНФЛІКТ_АРТИКУЛА, ЗМІНА_ІДЕНТИЧНОСТІ_АБО_КОМПЛЕКТУ, НЕМАЄ_ОПОРНОЇ_НАЗВИ, НЕВІДОМА_ВАЛЮТА, НЕВАЛІДНА_ЦІНА, НЕВІДОМА_НАЯВНІСТЬ, НЕВАЛІДНА_КІЛЬКІСТЬ. Плюс новий **КОНФЛІКТ_МОДЕЛІ**: діє лише коли постачальник передає `<model>`, а в картці є «Модель». Зараз у фіді постачальника `<model>` немає (аудит — 0%). Ізолюється лише рядок, решта фіду публікується |
| 2 | Не видаляти, не створювати дубль | Рядок лишається в каталозі й у фіді під тим самим Offer ID. Невідомий offer, схожий на картку, іде в ручну чергу (D1, п. 6) |
| 3 | Зберегти останні перевірені назву, опис, характеристики, SEO, фото, ціну | Незмінні колонки (печатки) не змінюються. План F:M для конфлікту, як і в LIVE, **не бере** нову ціну постачальника: F:H лишаються останніми перевіреними |
| 4 | Без власного залишку й перевіреної ціни — «Немає в наявності» | «-», знижка '', кількість ''. У YML `available="false"` і `<price>` = остання перевірена Base. Генератор відмовляється публікувати конфліктну картку як доступну. Картка без жодної перевіреної ціни ще не публікувалась, тому виключається з версії фіду |
| 5 | Власний залишок + достовірна ціна — продаж за окремим правилом | Обидві умови: (а) `state/own-stock.json` — qty > 0, підтвердження не старше 7 днів; (б) ціну перевірено успішним зіставленням не давніше **3 діб** (`policy.ownStockConflictPriceMaxAgeDays`; час — `operational.verifiedAt`). Тоді статус ВЛАСНИЙ_ЗАЛИШОК, «+», кількість = власний залишок. Інакше — п. 4 |
| 6 | Журнал: причина, Offer ID, старі/нові значення, дата | `journal/conflicts/<місяць>/<запуск>.json` — події **OPENED / CHANGED / RESOLVED**. Кожна подія: at, offerId, reason, previousReason, sale (UNAVAILABLE / OWN_STOCK / BLOCKS_FEED), old (ID, артикул, опорні назви, модель, остання перевірена ціна, наявність, verifiedAt), new (усе, що прийшло від постачальника). Повтор того самого конфлікту нової події не створює. Поточний реєстр — `reports/conflicts/latest.json` |
| 7 | Сумнівні нові товари не додавати автоматично | Фід містить лише ID погодженого паспорта, тож нові товари фізично не потрапляють у YML. Сумнівні — у `reports/identity` (MANUAL_REVIEW), решта — у звіті нових товарів для контенту й погодження. Аркуш «Заморожені ID» вважається відомим (`catalog.knownIdSheets`). Це зафіксований набір ID каталогу (5143 = 5029 main + 28 відкладених + 86 виключених за «Аудитом»; експорт 21.10), тож свідомо виключені товари не з'являються як «нові» |
| 8 | Після виправлення — звичайне оновлення тієї самої картки | Наступний успішний mtMatch → ЗІСТАВЛЕНО, нова ціна й наявність постачальника, подія RESOLVED, конфлікт знімається з реєстру |
| 9 | Багато проблем одночасно або системна помилка — не публікувати, зберегти справну версію, повідомити | Спільний поріг для нових ізоляцій (зникнення + конфлікти) за запуск: понад max(50, 2% каталогу) — синк ERROR. Стан, прив'язки, журнал і фіди не змінюються, Prom отримує останню справну версію. CLI повертає ненульовий код, тож у GitHub Actions запуск позначається як failed і надсилається сповіщення |
| 10 | Не змінювати товарні ID Prom без перевіреного зіставлення | YML `offer id` = наш стабільний Offer ID, `vendorCode` = збережений «Код товару Prom». Обидва в незмінних колонках, а склад ID фіду = погоджений паспорт. Перев'язка змінює лише внутрішній реєстр `links` |

Перевірено на реальних даних 21.10 (shadow-replay): 4 конфлікти (артикул, ціна 0, USD, інший комплект) + 3 зникнення + 5 перевипусків. Фід опубліковано, 4 картки ізольовано, 5/5 правильних перев'язок. На наступному прогоні конфлікти виправлено — 4 події RESOLVED.
